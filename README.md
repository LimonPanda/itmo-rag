# Повар_спрашивает_RAG

## Описание проекта
Кулинарный помощник, который предлагает пользователю рецепты на основе имеющихся ингредиентов,
используя Retrieval-Augmented Generation (RAG) поверх корпуса кулинарных рецептов.

## Задача
Разработать кулинарного помощника, который по списку ингредиентов,
введённых пользователем, находит наиболее релевантные рецепты
в корпусе кулинарных данных и формирует структурированный ответ.

## Ограничения и допущения
- Используется ограниченный корпус рецептов (~10 000).
- Пользователь может общаться на русском или английском языках, но ответы и рецепты будут на английском.
- Система не генерирует новые рецепты с нуля, а опирается на retrieval.

## Интерфейс и деплой
Пользователь вводит тип блюда (например, "суп") и список ингредиентов.
Система возвращает 2–5 релевантных рецептов (название).
После выбора одного рецепта пользователь получает полный рецепт, список ингредиентов и ссылку на источник.

Ограничение по типу блюда реализуется без разметки датасета: через учет ключевых слов в запросе и ранжирование по совпадению в title.

## Примеры использования

### Пример диалога с ботом

**Пользователь:**
```
Dinner
Salty
Beef, onions, potatoes, glue
```

**Бот:**
```
Understood request as:
- dish_type: —
- preferences: salty
- ingredients: beef, onions, potatoes

Found options. Choose a recipe:
1. Beef Stew With Potatoes
2. Steak 'N' Onion Pie
3. Japanese-Style "Meat and Potatoes"
4. Potato Salad with Sweet Corn, Bacon, and Red Onion
5. Beer-Flavored Potatoes

Make another query
```

После выбора рецепта бот показывает полный рецепт с инструкциями и ссылкой.

### Формат ввода пользователя
Пользователь вводит:
1) Описание запроса (свободным текстом): тип блюда + предпочтения.
   Пример: "суп, острое" / "паста, быстро" / "салат, легкий"
2) Список ингредиентов.
   Пример: "курица, картофель, лук"

Информация из запроса пользователя выделяется и структурируется LLM. Это добавляет свободу действий: можно просто скинуть чек из магазина и запрос будет обработан корректно.

## Данные

### Источник
Исходный датасет: RecipeNLG  
https://recipenlg.cs.put.poznan.pl/  

CSV-датасет с рецептами (title, ingredients, instructions, source_url, ...),
содержащий более 2 миллионов рецептов, собранных с различных кулинарных сайтов.

### Отбор данных
Для проекта используется подмножество рецептов, отфильтрованное по доменам источника:
- tasteofhome.com
- delish.com

На первом этапе было собрано подмножество из 55 474 рецептов:
- tasteofhome.com — 51 594
- delish.com — 3 880

Файл:  
`data/raw/tasteofhome_delish.csv`

Из этого подмножества был сформирован финальный корпус из **10 000 рецептов**:
- delish.com — 3 880 рецептов
- tasteofhome.com — 6 120 рецептов

Файл:  
`data/raw/recipes_10k.csv`

### Подготовка данных для RAG

Каждый рецепт рассматривается как один документ для retrieval.
Chunking не применяется, так как размер одного рецепта укладывается в допустимый контекст.

Финальный датасет хранится в формате JSON Lines (`.jsonl`):

`data/processed/recipes.jsonl`

#### Структура одного документа
- `id` — уникальный идентификатор рецепта
- `title` — название рецепта
- `ingredients_raw` — оригинальные ингредиенты с количествами
- `ingredients_normalized` — нормализованные ингредиенты без стоп-ингредиентов
- `instructions` — полный текст приготовления
- `source_url` — ссылка на оригинальный рецепт
- `text` — текстовое представление рецепта, используемое для эмбеддингов
  (title + ingredients_normalized + сокращённые instructions)

Часто встречающиеся ингредиенты (salt, sugar, butter и др.) исключены
из `ingredients_normalized`, чтобы уменьшить шум при retrieval,
но сохранены в `ingredients_raw` и тексте рецепта.

### Объём данных и примеры

- Финальный корпус: 10 000 рецептов
- Формат: JSONL
- Файл: `data/processed/recipes.jsonl`

Для просмотра структуры данных и примеров используется sample-файл:
- `data/processed/recipes_sample.jsonl` (20 рецептов)

## Архитектура

### Общая схема
Система реализует Retrieval-Augmented Generation (RAG) с детерминированным retrieval-ядром и использованием LLM исключительно для обработки пользовательского ввода (query parsing).  
LLM **не участвует в поиске по векторной базе** и не влияет на ранжирование кандидатов.

---

### Pipeline (Core RAG)

#### 1. Preprocessing запроса (LLM + fallback)
- пользователь может вводить запрос в произвольной текстовой форме (в т.ч. свободный текст или текст кассового чека);
- при наличии API-ключа используется LLM (Mistral) для извлечения структурированного запроса:
  - `dish_type` (тип блюда),
  - `preferences` (предпочтения),
  - `ingredients` (ингредиенты);
- LLM возвращает строго валидный JSON с полями на английском языке;
- при недоступности LLM используется fallback-парсер на правилах и словарях;
- итогом этапа является нормализованный retrieval-запрос вида: dish_type + preferences + ingredients


#### 2. Embedding
- используется локальная модель эмбеддингов:
`sentence-transformers/all-MiniLM-L6-v2`;
- для каждого рецепта формируется один embedding;
- эмбеддинги L2-нормализуются;
- поиск осуществляется по cosine similarity.

---

#### 3. Vector Store (FAISS)
- документы: один рецепт = один документ;
- индекс: `IndexFlatIP` по нормализованным embedding-векторам;
- артефакты индекса:
- `data/index/faiss.index`
- `data/index/doc_ids.json`

---

#### 4. Retrieval
- FAISS возвращает top-k кандидатов по embedding similarity;
- retrieval полностью детерминирован и не использует LLM.

---

#### 5. Reranking (нелинейная логика)
- итоговый скор кандидата вычисляется как: score = faiss_similarity + bonus_ingredient_overlap + bonus_dish_type_match
- бонус за пересечение ингредиентов с запросом пользователя;
- бонус за совпадение `dish_type` с ключевыми словами в `title`;
- **hard filter**: если пользователь указал ингредиенты, кандидат должен иметь минимум одно совпадение;
- данный этап реализует нелинейную логику поверх retrieval.

---

#### 6. Выдача результата
- пользователю возвращается 2–5 наиболее релевантных рецептов:
- название,
- совпавшие ингредиенты,
- ссылка на источник;
- после выбора рецепта используется полный текст рецепта (ингредиенты + инструкции);
- LLM на этом этапе не участвует в поиске и используется только для улучшения UX (опционально).

---

### Взаимодействие компонентов

- `rag/index.py`  
Построение FAISS-индекса из `data/processed/recipes.jsonl`.

- `rag/retriever.py`  
Реализация retrieval и reranking для одного пользовательского запроса.

- `rag/evaluate.py`  
Тестирование retrieval-ядра на валидационной выборке:
baseline (embedding-only) vs rerank (embedding + эвристики).

- `bot/bot.py`  
Telegram-интерфейс:
- приём пользовательского ввода;
- LLM-парсинг запроса;
- вызов retrieval;
- управление диалоговыми состояниями и навигацией.

---

## Валидация и метрики

### Валидационная выборка
Используется self-retrieval валидация:
- выбирается N рецептов;
- для каждого строится синтетический запрос из 3–5 ингредиентов `ingredients_normalized`
  (+ `soup`, если слово "soup" встречается в title);
- ожидаемый документ — исходный рецепт.

Файлы:
- `data/validation/queries.jsonl` — валидационные запросы
- `data/validation/results.json` — результаты и метрики

### Baseline
Baseline-решение: retrieval только по FAISS similarity (без reranking и фильтрации).

### Метрики качества (N=50, retrieve_k=25)
- baseline_hit@5: **0.36**
- baseline_hit@10: **0.42**
- baseline_mrr@10: **0.2903**
- rerank_hit@5: **0.52**
- rerank_hit@10: **0.52**
- rerank_mrr@10: **0.4967**

### Интерпретация
Reranking повышает качество retrieval по всем метрикам.
Наиболее заметный рост наблюдается по MRR@10 (0.29 → 0.50),
что означает более раннее появление релевантного рецепта в выдаче.

## 🚀 Запуск проекта через Docker

Проект можно запустить локально одной командой с использованием **Docker** и **Docker Compose**.  
Это рекомендуемый способ запуска.

### 1. Клонирование репозитория

```bash
git clone https://github.com/LimonPanda/itmo-rag
cd itmo-rag
```

### 2. Создание файла .env

В корне проекта необходимо создать файл `.env` со следующими переменными окружения:
```
BOT_TOKEN=<TELEGRAM_BOT_TOKEN>

LLM для парсинга пользовательского ввода
MISTRAL_API_KEY=<MISTRAL_API_KEY>
MISTRAL_MODEL=mistral-medium-latest # Можно менять, но от этого будет зависеть качество ответов
```

**Пояснения:**

- `BOT_TOKEN` — токен Telegram-бота (обязателен).
- `MISTRAL_API_KEY` — API-ключ Mistral (опционален).
- Если ключ не указан или API временно недоступно, система автоматически использует fallback-парсер без LLM.
- `MISTRAL_MODEL` — используемая модель Mistral (опционально).

⚠️ Файл `.env` не должен добавляться в репозиторий.

### 3. Запуск сервиса

Если индекс уже подготовлен (как в данной версии):
```bash
docker compose up --build
```

После запуска Telegram-бот становится доступен и готов к приёму запросов.

### 4. Хранение данных и моделей

- Папка `data/` монтируется как volume и сохраняется между перезапусками контейнера.
- Модели HuggingFace кэшируются в Docker volume и не скачиваются повторно при следующих запусках.

### Возможные ошибки и поведение системы

- Если LLM недоступна (например, ошибка 429 или отсутствует `MISTRAL_API_KEY`), бот уведомляет пользователя и автоматически использует fallback-режим обработки запроса.
- При первом запуске возможна задержка из-за загрузки embedding-моделей.
