# Повар_спрашивает_RAG

## Описание проекта
Кулинарный помощник, который предлагает пользователю рецепты на основе имеющихся ингредиентов,
используя Retrieval-Augmented Generation (RAG) поверх корпуса кулинарных рецептов.

## Задача
Разработать кулинарного помощника, который по списку ингредиентов,
введённых пользователем, находит наиболее релевантные рецепты
в корпусе кулинарных данных и формирует структурированный ответ.

Система должна:
- учитывать совпадение ингредиентов;
- опираться на реальные рецепты из корпуса;
- предоставлять ссылку на источник рецепта.

## Ограничения и допущения
- Используется ограниченный корпус рецептов (~10 000).
- Поддерживается один язык рецептов.
- Система не генерирует новые рецепты с нуля, а опирается на retrieval.

## Интерфейс и деплой
Пользователь вводит тип блюда (например, "суп") и список ингредиентов.
Система возвращает 2–5 релевантных рецептов (название + краткое обоснование).
После выбора одного рецепта пользователь получает полный рецепт, список ингредиентов и ссылку на источник.

Ограничение по типу блюда реализуется без разметки датасета: через учет ключевых слов в запросе и ранжирование по совпадению в title.


### Формат ввода пользователя
Пользователь вводит:
1) Описание запроса (свободным текстом): тип блюда + предпочтения.
   Пример: "суп, острое" / "паста, быстро" / "салат, легкий"
2) Список ингредиентов (через запятую).
   Пример: "курица, картофель, лук"

Предпочтения извлекаются из ограниченного словаря ключевых слов (без сложного NLP).
Если предпочтения не распознаны, система использует только тип блюда и ингредиенты.

### Поддерживаемые предпочтения (MVP)
- острое
- быстро
- простое
- сытное
- легкое
- вегетарианское
- куриное
- без мяса
- сливочное
- томатное

https://recipenlg.cs.put.poznan.pl/  

CSV-датасет с рецептами (title, ingredients, instructions, source_url, ...),
содержащий более 2 миллионов рецептов, собранных с различных кулинарных сайтов.

### Отбор данных
Для проекта используется подмножество рецептов, отфильтрованное по доменам источника:
- tasteofhome.com
- delish.com

На первом этапе было собрано подмножество из 55 474 рецептов:
- tasteofhome.com — 51 594
- delish.com — 3 880

Файл:  
`data/raw/tasteofhome_delish.csv`

Из этого подмножества был сформирован финальный корпус из **10 000 рецептов**:
- delish.com — 3 880 рецептов
- tasteofhome.com — 6 120 рецептов

Файл:  
`data/raw/recipes_10k.csv`

### Подготовка данных для RAG

Каждый рецепт рассматривается как один документ для retrieval.
Chunking не применяется, так как размер одного рецепта укладывается в допустимый контекст.

Финальный датасет хранится в формате JSON Lines (`.jsonl`):

`data/processed/recipes.jsonl`

#### Структура одного документа
- `id` — уникальный идентификатор рецепта
- `title` — название рецепта
- `ingredients_raw` — оригинальные ингредиенты с количествами
- `ingredients_normalized` — нормализованные ингредиенты без стоп-ингредиентов
- `instructions` — полный текст приготовления
- `source_url` — ссылка на оригинальный рецепт
- `text` — текстовое представление рецепта, используемое для эмбеддингов
  (title + ingredients_normalized + сокращённые instructions)

Часто встречающиеся ингредиенты (salt, sugar, butter и др.) исключены
из `ingredients_normalized`, чтобы уменьшить шум при retrieval,
но сохранены в `ingredients_raw` и тексте рецепта.

### Объём данных и примеры

- Финальный корпус: 10 000 рецептов
- Формат: JSONL
- Файл: `data/processed/recipes.jsonl`

Для просмотра структуры данных и примеров используется sample-файл:
- `data/processed/recipes_sample.jsonl` (20 рецептов)


## Архитектура

### Pipeline (Core RAG)
1) **Preprocessing запроса**
- из пользовательского ввода формируется retrieval-запрос (тип блюда + предпочтения + ингредиенты);
- ингредиенты пользователя нормализуются простым разбиением по запятым.

2) **Embedding**
- используется локальная модель эмбеддингов: `sentence-transformers/all-MiniLM-L6-v2`;
- эмбеддинги нормализуются, поиск выполняется как cosine similarity.

3) **Vector Store (FAISS)**
- документы: один рецепт = один документ;
- индекс: `IndexFlatIP` по нормализованным эмбеддингам;
- артефакты индекса:
  - `data/index/faiss.index`
  - `data/index/doc_ids.json`

4) **Retrieval**
- FAISS возвращает top-k кандидатов по similarity.

5) **Reranking (нелинейная логика)**
- итоговый скор = similarity + бонус за пересечение ингредиентов;
- бонус за совпадение dish_type в title;
- **hard filter**: если пользователь указал ингредиенты, кандидат должен иметь минимум 1 совпадение.

6) **Выдача результата**
- возвращается топ 2–5 рецептов с названием, ссылкой и совпавшими ингредиентами;
- полный рецепт используется далее для формирования финального ответа интерфейса.

### Взаимодействие компонентов
- `rag/index.py`: строит индекс FAISS из `data/processed/recipes.jsonl`
- `rag/retriever.py`: выполняет retrieval + rerank для одного пользовательского запроса
- `rag/evaluate.py`: запускает baseline vs rerank на валидационной выборке и считает метрики

## Валидация и метрики

### Валидационная выборка
Используется self-retrieval валидация:
- выбирается N рецептов;
- для каждого строится синтетический запрос из 3–5 ингредиентов `ingredients_normalized`
  (+ `soup`, если слово "soup" встречается в title);
- ожидаемый документ — исходный рецепт.

Файлы:
- `data/validation/queries.jsonl` — валидационные запросы
- `data/validation/results.json` — результаты и метрики

### Baseline
Baseline-решение: retrieval только по FAISS similarity (без reranking и фильтрации).

### Метрики качества (N=50, retrieve_k=25)
- baseline_hit@5: **0.36**
- baseline_hit@10: **0.42**
- baseline_mrr@10: **0.2903**
- rerank_hit@5: **0.52**
- rerank_hit@10: **0.52**
- rerank_mrr@10: **0.4967**

### Интерпретация
Reranking повышает качество retrieval по всем метрикам.
Наиболее заметный рост наблюдается по MRR@10 (0.29 → 0.50),
что означает более раннее появление релевантного рецепта в выдаче.
